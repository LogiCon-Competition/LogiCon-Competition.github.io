LogiCon Competition

Logical consistency and verifiable reasoning under realistic constraints.

LogiCon is a competition proposal for evaluating whether AI systems can reason reliably under explicit logical constraints, multi-step dependencies, and adversarially structured inputs. This website is the public hub for the proposal and, if accepted, the competition launch.

Operating model

Keep the website static; run submissions elsewhere.

A GitHub Pages website should not collect submissions or run evaluations. It should be the stable public front door: task definition, rules, timeline, dataset links, starter code, leaderboard links, FAQ, and organizer contacts.

The competition platform should handle registration, submissions, validation, scoring logs, leaderboard phases, and final ranking.

Recommended architecture

  • Website: GitHub Pages organization site.
  • Submissions: Codabench by default; Kaggle if the task is a standard prediction challenge.
  • Data: Hugging Face Datasets or Zenodo, mirrored through the platform if useful.
  • Code: GitHub starter kit with validation and baseline scripts.
  • Discussion: Google Group plus optional Discord.

Submissions

Use a dedicated platform, not a custom web form.

The live competition page will be linked here after the platform is configured. Participants should submit through a purpose-built competition platform so scoring, logs, leaderboards, limits, and invalid attempts are handled consistently.

Default recommendation: Codabench. It is well suited for academic competitions with custom scoring programs, phases, public/private leaderboards, and reproducible bundles.

Planned participant flow

  1. Register on the competition platform.
  2. Download data and starter kit from links on this website.
  3. Run local validation with the starter kit.
  4. Upload predictions, or code only if code submission is required.
  5. Platform validates, scores, logs, and updates the relevant leaderboard.

Prediction files first

Prefer CSV/JSONL prediction-file submissions for the main track. They are cheaper, simpler, safer, and easier to reproduce. Use code submissions only if hidden data must be processed inside a controlled environment.

Data release

Make data public, versioned, and auditable.

LogiCon should provide enough public data for participants to develop systems, while keeping final labels or final instances protected. Data hosting should be separate from this static website.

Recommended: host public data and a dataset card on Hugging Face Datasets or Zenodo. Keep hidden labels inside the scoring bundle or platform-protected private split.

Data splits

  • Practice: small labeled examples and output format.
  • Development: labeled data for local validation.
  • Public test: hidden labels for active leaderboard feedback.
  • Private final test: hidden labels for final ranking.

Data package checklist

  • Dataset card, license, citation, and known limitations.
  • Stable release tags and checksums.
  • Example submission and schema validator.
  • Policy for external data, pretrained models, tools, and manual annotation.

Evaluation

Use an automated scoring bundle with viability checks.

The evaluation should be executable, deterministic where possible, and versioned. Organizers should be able to re-run submissions, inspect logs, and reproduce final rankings.

Viability gate: every submission should pass format validation, completeness checks, ID checks, resource-limit checks, and baseline sanity tests before it receives a score.

Evaluation layers

  1. Schema validation: required columns, IDs, and answer format.
  2. Integrity checks: file size, duplicates, missing IDs, and leakage indicators.
  3. Scoring: primary metric, diagnostic metrics, and tie-breakers.
  4. Robustness audit: slices for perturbations or out-of-distribution cases.
  5. Final verification: method report and reproducibility materials for top teams.

Metric placeholder

Primary metric: to be finalized for the exact task. Candidate families include exact-match consistency, proof validity, contradiction rate, calibrated accuracy, or a composite logical-reasoning score.

Tie-breakers: invalid-output rate, contradiction rate, compute budget, and earlier valid submission timestamp.

Tracks

Proposed competition tracks

Track A · Prediction

Participants submit answers for hidden benchmark instances. This is the simplest and most robust track for broad participation.

Track B · Explanation

Participants submit structured justifications, proofs, rationales, or traces that can be checked for validity and consistency.

Track C · Robustness

Participants are evaluated on distribution shifts, adversarial variants, or consistency under perturbations.

Rules

Participation rules to finalize before launch

Rules should be explicit before the leaderboard opens. Ambiguity creates avoidable disputes and weakens the proposal.

  • Eligibility and team-size limits.
  • Submission limits per day and per phase.
  • Allowed external data, model use, prompting, tools, and human annotation.
  • Public/private leaderboard split and final ranking procedure.
  • Policy for duplicate accounts, data leakage, manual test-set inspection, and disqualification.
  • Top-team reproducibility package before awards are confirmed.

FAQ

Frequently asked questions

Will submissions be made on this website?

No. This website is static and should remain a stable information hub. Submissions should be made through Codabench, Kaggle, EvalAI, or another dedicated platform.

How will hidden test labels be protected?

Final labels should not be included in public files. They should live inside the protected scoring environment, private platform data, or organizer-controlled scoring bundle.

How will invalid submissions be handled?

The scoring program should first run validation checks. Invalid submissions should receive clear error messages and no leaderboard score unless the platform records them separately as failed attempts.
