LogiCon Competition

Logical contradiction detection for LLM-based systems

Real-world knowledge is heterogeneous, evolving, and not always mutually consistent. LogiCon evaluates whether LLM-based systems can detect logical contradictions in verbalized statements extracted from real knowledge graphs, including cases where the semantic context is explicit and cases where models must infer the missing assumption.

Overview

Detect contradictions grounded in knowledge-source semantics

LLM systems increasingly reason over external evidence from retrieved documents, knowledge graphs, and domain databases. These sources may disagree because of temporal change, ambiguity, provenance differences, or modeling assumptions. In applications such as retrieval-augmented generation, fact verification, question answering, recommendation, and knowledge-base integration, undetected contradictions can lead to unreliable outputs.

LogiCon turns this into a controlled evaluation task: given externally provided assertions, systems must decide whether the statements can jointly hold under the semantics of the source knowledge graph.

What makes LogiCon different?

  • Contradictions are extracted from real-world knowledge graphs rather than written as synthetic sentence pairs.
  • Examples are organized by the semantic source of incompatibility, such as disjointness, hierarchy, direct negation, and cardinality constraints.
  • Explicit settings include the semantic context needed to detect the contradiction.
  • Implicit settings omit that context, requiring systems to infer the relevant background assumption.

Goal for participants

Build, prompt, fine-tune, retrieve, or otherwise adapt LLM-based systems so that they become more aware of contradictory statements, especially in the implicit setting where the semantic basis of the conflict is not directly provided.

Data and tracks

Benchmarks across contradiction types, explicitness levels, and domains

LogiCon uses common-knowledge data derived from Wikidata and biomedical data derived from ProteCon, which combines Gene Ontology annotations with STRING-based protein data. Wikidata-derived tracks include English, Spanish, and French verbalizations; and Chinese, German and Portuguese labelled triples when coverage is possible; the biomedical HierarCon track is in English.

Wikidata-derived data

Structured common-knowledge claims with qualifiers and constraints. Tracks cover disjoint class axioms, disjoint instance axioms, and cardinality constraints.

ProteCon / GO data

Biomedical protein annotations embedded in the Gene Ontology hierarchy. Tracks cover direct negation and hierarchically inferred contradictions.

Explicit and implicit variants

Most contradiction types include an explicit version with the relevant semantic context and an implicit version where that context is omitted. Direct negation appears only in an explicit format.

Evaluation

Measure performance and the explicit–implicit gap

Participants submit one prediction per instance using the official submission format. CodaBench validates the file and computes the final ranking. Reference baselines will include open-source zero-shot instruction-following LLMs using the same prompts across tracks, plus a simple context-aware prompting baseline for explicit settings.

The competition reports standard classification metrics, including macro-F1, accuracy, precision, and recall. The main challenge is to improve performance on implicit datasets and reduce the gap between explicit and implicit settings.

Primary comparison

Main metrics are Accuracy and Macro F1, supported by peformance changes between the explicit and implicit settings for all classification metrics.

The explicit–implicit gap for a metric M is:

ΔM = Mexplicit − Mimplicit

Lower gaps indicate more robust reasoning when the relevant semantic context is omitted. Negative values are possible but not expected under equal evaluation procedures.

Final ranking

Public leaderboard submissions are used during validation. Final rankings are computed only on hidden test labels after the final submission deadline.

Rules and engagement

Participant rules

These rules are intended to evaluate contradiction detection from the provided statements, not reverse-engineering of the dataset construction process.

Allowed approaches

  • Prompting, fine-tuning, retrieval-augmented methods, open-source models, and commercial APIs are allowed.
  • All external resources, models, prompts, and datasets used by a team must be disclosed in the final system description.
  • Participants provide their own compute resources; no special hardware platform is required.

Submission requirements

  • Predictions must be submitted only through the official CodaBench competition platform.
  • Each submission must follow the released official format and contain one prediction per instance.
  • Validation submissions per team per day and final test submissions will be limited to reduce overfitting.

Prohibited behavior

  • Do not manually label validation or test instances.
  • Do not share hidden test predictions across teams.
  • Do not reconstruct hidden labels by querying the source knowledge graphs using instance identifiers or other leakage cues.

Result verification

Organizers may request code, prompts, logs, outputs, or other methodological details from top-ranked teams before confirming final rankings. Teams should be prepared to document their method and external resources used.

FAQ

Frequently asked questions

Will submissions be made on this website?

No. Submissions should be made through the official CodaBench link once it is available.

Can teams use commercial APIs?

Yes. Commercial APIs are allowed, provided that all external resources and models are disclosed in the final system description.

Can teams query any of the data sources used to recover labels?

No. Participants must not attempt to reconstruct hidden validation or test labels by querying source knowledge graphs with instance identifiers or leakage cues.
