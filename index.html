Benchmarking LLM-based Contradiction Detection

Operating model

The website is the hub. Codabench runs the competition.

GitHub Pages should stay static, reliable, and easy to archive. It should not collect uploads or run evaluation. Instead, it should link participants to the competition platform, dataset release, starter kit, rules, discussion channel, and leaderboard.

Codabench will be the default place for registration, submissions, scoring logs, leaderboard phases, and final ranking. The fields below are ready for the final Codabench URLs once the competition page is created.

  • Competition platform: Codabench page for tasks, phases, submissions, and leaderboard.
  • Data: Codabench-hosted public files
  • Baseline Code: GitHub support kit with baseline and example submission.
  • Discussion: Discord channel URL

Submissions

Use Codabench submissions, not a custom form.

Participants should upload through Codabench so that submission limits, scoring logs, public/private phases, and failed submissions are handled consistently.

Default recommendation: start with CSV/JSONL prediction-file submissions. They are cheaper, safer, easier to debug, and more reproducible than executable-code submissions.

Participant flow

  1. Register on Codabench.
  2. Download data and starter kit from this website.
  3. Run local validation with the starter kit.
  4. Upload predictions to the Codabench submission phase.
  5. Codabench validates, scores, logs, and updates the leaderboard.

When to use code submissions

Use executable submissions only if hidden data must be processed by each participant system inside a controlled environment. Otherwise, prediction files are more robust.

Data release

Make data public, versioned, and auditable.

LogiCon should provide enough public data for participants to develop systems, while keeping final labels or final instances protected. Data can be exposed through Codabench for convenience and mirrored on a long-term archive such as Hugging Face Datasets or Zenodo.

Recommended: host practice/dev data and sample submissions publicly; keep private final labels inside the Codabench scoring bundle or protected private split.

Data splits

  • Practice: small labeled examples and output format.
  • Development: labeled data for local validation.
  • Public test: hidden labels for leaderboard feedback.
  • Private final test: hidden labels for final ranking.

Data package checklist

  • Dataset card, license, citation, and known limitations.
  • Stable release tags and checksums.
  • Example submission and schema validator.
  • Policy for external data, pretrained models, tools, and manual annotation.

Rules

Participation rules to finalize before launch

Rules should be explicit before the leaderboard opens. Ambiguity creates avoidable disputes and weakens the proposal.

  • Eligibility and team-size limits.
  • Allowed external data sources, model use and prompting.
  • Public/private leaderboard split and final ranking procedure.
  • Policy for duplicate accounts, data leakage, manual test-set inspection, and disqualification.
  • Top-team reproducibility package before awards are confirmed.

FAQ

Frequently asked questions

Will submissions be made on this website?

No. This website is static and should remain a stable information hub. Submissions should be made through Codabench or another dedicated platform.

Where will the data live?

The public dataset can be linked from Codabench and mirrored through a long-term repository. Hidden final labels should remain protected inside the scoring setup.

How will invalid submissions be handled?

The scoring program should first run validation checks. Invalid submissions should receive clear error messages and no leaderboard score unless the platform records them separately as failed attempts.
